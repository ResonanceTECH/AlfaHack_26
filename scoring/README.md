# Скоринг и AI-помощник

## Первый запуск

**Из корневой папки репозитория выполните одну команду:**

```bash
docker compose up --build
```

Нужны установленный Docker с Compose и интернет. Других подготовительных
команд нет. При первом запуске система сама скачает
Qwen3-4B-Instruct-2507 Q4_K_M, проверит SHA256, запустит модель, backend и интерфейс.
Отдельно скачивать веса, устанавливать Python или получать ключ API не нужно.

Дождитесь завершения загрузки и запуска сервисов, затем откройте
**http://localhost:8080**.

**Вход клиента:** `ip@demo.alfa`, пароль `demo1234`.

Файл модели занимает около 2,5 ГБ; загрузка может занять несколько минут.
Кроме диска нужна свободная RAM для модели и контекста: около 6 ГБ доступной
памяти — практический ориентир для первого теста, а не измеренный минимум.
Если страница ещё недоступна, посмотрите сообщения в терминале: интерфейс
запускается после готовности модели и backend.

При следующих запусках используется сохранённая модель — повторная загрузка
не нужна. Для запуска в фоне добавьте `-d`:

```bash
docker compose up -d --build
```

## Что проверить в интерфейсе

1. Войдите в кабинет и выберите компанию ИП Петрова.
2. Откройте **«Подбор»**, задайте цель, сумму и срок. Выбранный продукт
   можно использовать для создания и отправки заявки.
3. В **«Моих заявках»** откройте карточку новой отправленной заявки.
   Через кнопку **«Объяснить решение и задать вопрос»** перейдите к помощнику.
   Например: «Почему по заявке принято такое решение?» или
   «Как повлияла долговая нагрузка?».
4. Для подбора до подачи заявки откройте **«AI-консультант»** без контекста заявки.
   Напишите: «Нужен станок, 2,5 млн на 24 месяца». Если не указать сумму или срок,
   помощник предложит их уточнить.
5. Для проверки другого клиента используйте `ooo@demo.alfa` с тем же паролем:
   заявки первой компании ему недоступны.

Помощник отвечает по сохранённым результатам расчёта и опубликованному каталогу.
Вопрос вне этих данных должен получить ответ об отсутствии сведений.
Ошибка соединения отображается как ошибка, а не подменяется демо-перепиской.

Скоринг и помощник работают с синтетическими данными. Решение принимает
детерминированное ядро; LLM объясняет причины и не обещает выдачу денег.
Если модель недоступна или её текст не прошёл проверку, backend возвращает
шаблонное объяснение по тем же фактам.

## Как устроен запуск

В корневом Compose описаны:

| Сервис | Назначение |
| --- | --- |
| model-download | Скачивание и проверка модели при первом запуске |
| llm | Локальный сервер Qwen |
| db и redis | Данные и служебное хранилище |
| api | Обработка заявок, скоринг и помощник |
| web | Веб-интерфейс |

Веса сохраняются в Docker volume `llm_models`. Загрузка идёт во временный файл;
модель становится доступна серверу только после проверки контрольной суммы.
При повторном запуске проверенный файл используется повторно.
Если загрузка не удалась, она повторяется; после исчерпания попыток причина
остаётся в логах, а модель с повреждённым файлом не запускается.

Загрузка весов → готовность модели → backend → интерфейс. Поэтому первая
сборка дольше повторных запусков.

Используется [Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)
с открытыми весами Apache-2.0,
[GGUF Q4_K_M от Unsloth](https://huggingface.co/unsloth/Qwen3-4B-Instruct-2507-GGUF)
и CPU-сервер llama.cpp. Платных API нет. Ревизия и SHA256 весов зафиксированы
непосредственно в сервисе model-download корневого Compose. Отдельный скрипт
для запуска не требуется. Источники и лицензии:
[THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md).


## Проверка разработчиком

Из корня репозитория, Python 3.11+; для полного backend рекомендуется 3.12:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install --timeout 120 --retries 10 -r backend/requirements.lock
python -m pip install -e ./scoring
python -m pytest -q
```

Автотесты проверяют расчёты, офферы, доступ к данным, ошибки модели и загрузку
весов с проверкой хеша. Для тестов не нужно скачивать настоящую модель:
используются небольшие фикстуры и заглушки.

## Как рассчитывается скоринг

Вместо обученной на клиентских данных модели используется экспертная скоркарта.
Для каждого показателя вычисляется значение, выбирается интервал и начисляются
баллы. Итоговая формула:

```text
Скор = 500 + сумма фактических вкладов факторов
```

| Фактор | Как определяется | Исходный диапазон вклада |
| --- | --- | --- |
| Возраст бизнеса | Полные месяцы с даты регистрации | −40…+30 |
| Динамика выручки | Выручка за 12 месяцев / выручка предыдущего периода − 1 | −40…+25 |
| Операционная маржа | (Выручка − расходы) / выручка | −50…+30 |
| Долговая нагрузка | Текущие платежи по кредитам / среднемесячная выручка | −50…+30 |
| Масштаб запроса | Сумма заявки / среднемесячная выручка | −45…+25 |
| Количество просрочек | Число просрочек за 12 месяцев | −60…+30 |
| Длительность просрочек | Максимальная длительность за 12 месяцев | −50…0 |
| Отрасль | Группа риска по первым двум знакам ОКВЭД | −25…+15 |

Например, маржа от 15% даёт +30 баллов, отрицательная маржа — −50.
Долговая нагрузка ниже 10% даёт +30, а от 40% — −50. Это экспертные баллы,
а не коэффициенты, полученные обучением, и не вероятность дефолта.

Количество и длительность просрочек связаны, поэтому их **общий вклад ограничен
снизу −60 баллами**. Это уменьшает двойной штраф за одну кредитную историю.
Динамика не применяется к бизнесу младше года или без сопоставимого прошлого периода.
На согласованных полных данных итоговый диапазон составляет **220–685**.

| Уровень риска | Скор |
| --- | --- |
| A | от 600 |
| B | от 520 до 599 |
| C | от 440 до 519 |
| D | ниже 440 |

Баллы не отменяют стоп-правила: недействующая компания, возраст меньше трёх
месяцев или текущая просрочка приводят к отказу. Налоговые проблемы и отсутствие
синтетических сведений о кредитной истории или налоговом статусе требуют ручного
рассмотрения, если нет более приоритетной причины отказа. Без обязательных данных
о регистрации или финансах запрашивается дополнение сведений.

Далее политика продукта определяет условия:

```text
Лимит суммы = минимум(
    лимит уровня риска,
    лимит продукта,
    допустимая кратность × среднемесячная выручка
)
```

Одинаковый риск даёт разные условия для оборотного кредита, овердрафта,
оборудования и экспресс-кредита. Например, для оборотного кредита уровня A
лимит — до шести месячных выручек, для B — до четырёх, для C — до двух.
Ставки и сроки также задаются политикой. Если исходные параметры нужно изменить,
формируется встречное предложение, которое повторно оценивается на новых
сумме и сроке. Исходная оценка и оценка оффера хранятся отдельно.

Все пороги, баллы и продуктовые условия находятся в
[scoring.yaml](credit_scoring/config/scoring.yaml), версия 2026.2-draft.
Конфиг проверяется при загрузке: интервалы и баллы должны быть согласованы,
а более низкий риск не должен получать худшие лимиты и ставку.

Упрощения прототипа: все данные синтетические, веса не откалиброваны на реальной
выборке, платёж овердрафта считается аннуитетом. Неполный скор нельзя сравнивать
с полным. Подбор продукта не равен одобрению кредита. LLM не меняет решение:
она получает проверенные факты, а её текст проходит структурные и эвристические
проверки. Они не гарантируют истинность каждой формулировки, поэтому предусмотрен
шаблонный резерв.
