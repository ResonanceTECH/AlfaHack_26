# Контекст проекта для агента: цифровой кредитный конвейер МСП (Alfa hack 2026)

Документ описывает задачу, принятые решения, текущее состояние кода и что делать дальше. Читать целиком перед любыми изменениями. Раздел «Решено» не пересматривать без согласования с владельцем, раздел «Предложено» можно улучшать, но с объяснением.

## 1. Кто и что

- Владелец репозитория работает в команде хакатона как MLE (ML-инженер). Общается по-русски. Документацию, комментарии для пользователей и тексты интерфейса писать по-русски, идентификаторы в коде по-английски.
- Задача хакатона: прототип цифрового кредитного конвейера для малого и микробизнеса. Клиент проходит путь от потребности до результата по заявке, банк управляет обработкой в едином продукте.
- Жюри запускает решение само, поэтому главное: рабочий сквозной сценарий, воспроизводимый запуск, понятная документация. Красивые экраны без связной логики не оценивается.

## 2. Требования кейса (источник: текст кейса организаторов)

Критерии успеха: целостность сквозного процесса, готовность к проверке, качество UX для клиента и банка, согласованность модулей (данные сохраняются, статус заявки меняется последовательно), enterprise-ориентированность (безопасность, надёжность, отказоустойчивость, масштабирование, сопровождение), потенциал развития. ИИ приветствуется, но не обязателен и не должен заменять работоспособность основного сценария.

Жёсткие ограничения:
- Только веб-интерфейс, мобильное приложение запрещено.
- Проверяемая версия не зависит от платных подписок, платных API, покупных данных и закрытых лицензий.
- Только синтетические данные (клиенты, компании, сотрудники, документы, заявки, финпоказатели). Команда создаёт их сама, организаторы данных не предоставляют.
- Нет доступа к системам Альфа-Банка. БКИ, ЕГРЮЛ/ЕГРИП, «Прозрачный бизнес» ФНС воспроизводятся локальными моками. Подписание документов и выдача денег симулируются.
- Весь пользовательский сценарий внутри продукта: без email, SMS, мессенджеров и звонков.
- LLM, если используются, только с открытыми весами.
- Допустима упрощённая, явно описанная логика кредитного решения.

Дополнительные рекомендации организаторов (из пересказа владельца):
- регистрация не нужна, авторизация нужна, интеграция с банком не нужна;
- адаптивная вёрстка и админ-панель с аналитикой (продумать ролевую модель) считаются плюсом;
- решение должно быть конфигурируемым, чтобы запускаться на моделях организаторов (открытые веса, не более 120 млрд параметров), можно несколько моделей под разные задачи;
- должно работать на обычном ПК (8 ядер), без тяжёлых компонентов;
- ИИ-ассистент и показ того, на чём модель основывает решение, считаются большим плюсом; тесты плюсом.

Обязательный комплект сдачи:
- GitHub с историей коммитов, тег или commit hash на момент дедлайна (приватный репозиторий: дать доступ аккаунту `alfa-hack-2026`);
- запуск в Docker одной воспроизводимой командой на обычном ПК;
- lock-файлы или зафиксированные версии;
- `README.md`: назначение, архитектура, требования, запуск, переменные окружения, компоненты, пошаговый сценарий проверки;
- синтетические данные и тестовые учётки для сквозного сценария;
- `THIRD_PARTY_NOTICES`: сторонние компоненты, модели, датасеты, сервисы и список смоделированных интеграций;
- в репозитории: архитектурная схема, описание API, OpenAPI/Swagger, коллекция запросов, диаграмма состояний заявки, модель данных, тестовые сценарии.

Неясность: в конце постановки кейса есть фраза про «новостную ленту, которая меняется под клиента». Остальной текст кейса новостей не касается, похоже на артефакт от другого кейса. Не реализовывать без уточнения у организаторов. Если уточнят, достаточно простой персонализированной ленты подсказок по статусу и отрасли клиента.

## 3. Решено владельцем

- Стек скоринга: Python 3.11+, PyYAML, pytest. Pydantic v2 для API-слоя (модели ядра сделаны на стандартных dataclasses, они совместимы).
- В MVP четыре продукта: оборотный кредит (`working_capital`), овердрафт (`overdraft`), кредит на оборудование (`equipment`), экспресс-кредит (`express`).
- Одна общая скоркарта для всех продуктов. Различие условий между продуктами задаёт кредитная политика. Это прямой тезис кейса: одинаковая оценка риска даёт разные условия для разных продуктов.
- Синтетические данные генерирует собственный генератор с фиксированным seed.

## 4. Предложено, но не подтверждено (можно менять)

- Backend: FastAPI + PostgreSQL + Alembic. Frontend: адаптивный SPA (React или Vue).
- Моки внешних сервисов отдельными контейнерами: `bki-mock`, `egrul-mock`, `fns-mock`, с управляемыми задержками и сбоями.
- LLM в отдельном контейнере (Ollama или llama.cpp server) за OpenAI-совместимым API. Роли моделей в конфиге: `llm_main`, `llm_light`, `embedder`. Для CPU реалистичны модели 3-9B в квантизации Q4, например семейства Qwen и Gemma; проверить лицензии перед внесением в `THIRD_PARTY_NOTICES`. Отключать режим «thinking» у ассистента.
- Роли: клиент, операционист банка (проверка полноты, запросы уточнений), кредитный аналитик (ручные решения), администратор (аналитика, пользователи, конфиг).
- Жизненный цикл заявки: Черновик, Подана, Проверка полноты (может вернуть в Требуется уточнение), Обогащение данными, Скоринг, Решение (авто или ручное), Оффер или Отказ, Принятие оффера, Подписание (симуляция), Выдача (симуляция), Закрыта; побочные: Отозвана клиентом, Истёк срок оффера. Каждый переход пишется в историю с автором, временем, причиной. Недопустимые переходы запрещены.
- Ключевой принцип: решение принимает детерминированный скоринг, LLM не принимает и не проверяет решения. LLM допустим только для подбора продукта на входе (диалог, предзаполнение заявки), объяснения результата простыми словами (по структурированным факторам, не «из головы») и сводки для аналитика. Основной сценарий обязан проходить с выключенным LLM, тексты тогда шаблонные.
- Отказоустойчивость для демо: таймауты и ретраи к мокам; если БКИ или ФНС недоступны, заявка уходит в ручное рассмотрение, а не падает. Идемпотентные операции, healthcheck-и, структурные логи, audit log действий.
- «Бегунки»: клиент двигает сумму и срок, эндпоинт `/preview` пересчитывает предварительное решение теми же `score(...)` без LLM. Помечать как предварительную оценку; не показывать точные пороги правил, только факторы и направление.

## 5. Текущее состояние кода

Архив `credit_scoring.zip` (пакет `credit_scoring`), структура:

```
credit_scoring/
  models.py        контракт входа и выхода (dataclasses), to_jsonable
  config.py        загрузка и валидация YAML
  config/scoring.yaml   стоп-правила, факторы, уровни риска, политика продуктов
  engine.py        score(input, config) - чистая функция
  generator.py     personas() и generate_batch(n, seed)
  cli.py           python -m credit_scoring.cli personas | generate
tests/             23 теста (config, generator, engine)
data/              personas.json, applications.jsonl (seed 42, 200 заявок)
```

Как работает `score`:
1. Если нет `egrul` или `financials`, результат `request_data` со списком недостающего.
2. Считаются признаки, применяются стоп-правила: `reject` ведёт к отказу, `manual_review` к ручному рассмотрению. Недоступные `fns` и `bki` (значение `None`) дают `manual_review`, а не ошибку.
3. Скоркарта: базовые 500 баллов плюс баллы по корзинам факторов (возраст бизнеса, динамика выручки, маржа, долговая нагрузка, сумма к выручке, число и длительность просрочек, группа риска отрасли). Уровни: A от 600, B от 520, C от 440, иначе D. В версии 2026.2-draft общий штраф истории ограничен −60 через YAML; динамика к бизнесу младше года не применяется. Согласованный полный диапазон 220–685, размах 465 (до ограничения истории: 170–685).
4. Политика продукт x уровень: лимит суммы = min(лимит уровня, лимит продукта, кратность месячной выручки), срок ограничен. Если запрос в лимитах, `approved`, если пришлось урезать сумму или срок, `counter_offer`. Уровень без записи в политике (включая D) или лимит ниже минимума продукта дают `rejected`. Для уровней с `auto_approve: false` и при `manual_review`-правилах результат `manual_review` с предварительным оффером.
5. Результат содержит решение, скор, уровень, оффер (сумма, срок, ставка, аннуитетный платёж), факторы с баллами, сработавшие правила, коды причин, версию конфига. В 2026.2-draft добавлены score_complete (наличие всех четырёх источников), offer_score, offer_risk_band и offer_factors. Исходный скор сохранён, условия оффера переоцениваются на предложенных сумме/сроке до устойчивости. points — фактический вклад; raw_points показывает исходный вклад при ограничении группы. Это готовая основа объяснимости и audit log.

Проверено у автора: все 23 теста проходят мини-раннером; мутационная проверка (порча движка и конфига) тесты ловит. Восемь персон (`ideal`, `ambitious`, `controversial`, `overdue`, `young`, `liquidating`, `incomplete`, `bki_down`) попадают в ожидаемые ветки.

## 6. Известные ограничения и честные оговорки

- Тесты запускались не через pytest (в песочнице автора не было сети), а мини-раннером. Первое действие: выполнить `pip install -r requirements.txt && python -m pytest tests` и исправить, если что-то отличается.
- Веса скоркарты и политика экспертные и не откалиброваны. Не обучать ML-модель на синтетике, размеченной этими же правилами (получится замкнутый круг). Если нужен ML, то как референс для сравнения, а в продукте остаётся скоркарта. В документации так и писать: «экспертная скоркарта, конфигурируема, заменяема на статистическую модель с тем же интерфейсом».
- Распределение решений на синтетическом батче (примерно 35% counter_offer, 28% отказов, 19% ручных, 14% одобрений) определяется допущениями генератора. Нельзя подавать как метрику качества.
- Платёж по овердрафту считается как аннуитет, это упрощение, его нужно явно описать.
- ИНН в данных вымышленные и не проходят проверку контрольной суммы. Это нужно сохранить, чтобы не пересечься с реальными компаниями.
- Не известны: срок до дедлайна, состав команды, объём RAM на целевой машине, будет ли жюри подавать собственные тестовые данные. Если будет, входная схема должна быть строго документирована и терпима к пропускам.

## 7. Рекомендуемый порядок работ

P0 (без этого сдавать нечего):
1. Проверить и закрепить ядро: pytest, lock-файлы, структура репозитория.
2. Диаграмма состояний заявки и модель данных (БД), затем API (FastAPI) поверх `score`, OpenAPI.
3. Авторизация и RBAC, кабинеты клиента (выбор продукта, форма, таймлайн статуса) и сотрудника (очередь, решение с обязательным комментарием при переопределении).
4. Моки БКИ, ЕГРЮЛ, ФНС и обогащение данных.
5. Docker Compose с запуском одной командой, сиды, README, `THIRD_PARTY_NOTICES`.

P1:
- эндпоинт `/preview` и бегунки; экран объяснения решения (таблица: фактор, значение, вклад в баллы, влияние) плюс сработавшие правила;
- ассистент подбора продукта и текстовое объяснение решения с шаблонным резервом;
- запрос уточнения с возвратом клиенту; админ-аналитика (воронка, время обработки, доли исходов, причины отказов, доля ручных решений и сбоев источников);
- коллекция запросов, тестовые сценарии e2e (идеальный клиент, отказ, другие условия, уточнение, недоступный источник), адаптив.

P2:
- распознавание документов (синтетическая отчётность) с подтверждением клиентом, помощник аналитика, персонализированные подсказки, деплой на бесплатный хостинг.

Также подготовить краткий блок исследования потребностей (JTBD, пара job stories, привязанных к экранам): жюри оценивает связь между потребностями и решением, но не терпит формального использования методик.

## 8. Правила для агента

Актуализация реализации: ядро подключено к workflow через backend/app/services/scoring.py.
Модуль LLM-агента реализован в backend/app/services/credit_agent: клиентские разъяснения,
сводка аналитика, вопросы по заявке, подбор опубликованных продуктов. Роль и доступ
проверяет backend, preview считает ядро, шаблонный режим работает без модели.
Проверки LLM используют заглушки; живой инференс и производительность пока не проверены.
Инструкция и контракт: backend/app/services/credit_agent/README.md.

- Контракт в `models.py` и семантику решений не менять молча: от них зависят backend и frontend. Любое изменение сопровождать тестом и пометкой в README.
- Правила, веса и политика только в YAML, без хардкода в коде. После правок конфига должен проходить `validate_config`.
- `score` остаётся чистой функцией: без сети, без LLM, без случайности, без записи в БД.
- Не добавлять платные API, закрытые модели и датасеты с неясной лицензией. Каждый новый внешний компонент вносить в `THIRD_PARTY_NOTICES`.
- Секреты через переменные окружения, пароли хешировать, RBAC проверять на уровне API, а не только в интерфейсе.
- Каждая новая функция идёт с тестом. Для LLM в CI использовать замоканный клиент.
- Фиксировать версии зависимостей и образов. Не коммитить сгенерированные тяжёлые файлы данных, если их можно воспроизвести командой с seed.
- Если требование кейса неясно, остановиться и спросить владельца, а не додумывать.
